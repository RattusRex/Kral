# Диагностика отправки писем подтверждения (issue #197)

## Установленная причина

В первоначально опубликованной SMTP-конфигурации было указано:

```text
SMTP_HOST=epohakostyastrof@gmail.com
```

`SMTP_HOST` должен содержать имя SMTP-сервера, а не адрес отправителя. Для
Gmail правильное значение — `smtp.gmail.com`. При старом значении backend
пытался установить SMTP-соединение с адресом электронной почты как с именем
сервера, поэтому доставка не могла начаться.

Правильная схема для Gmail и порта 587:

```text
EMAIL_BACKEND=smtp
SMTP_HOST=smtp.gmail.com
SMTP_PORT=587
SMTP_SECURITY=starttls
SMTP_USERNAME=epohakostyastrof@gmail.com
SMTP_PASSWORD=<пароль приложения Google>
SMTP_FROM_EMAIL=epohakostyastrof@gmail.com
```

Обычный пароль аккаунта Google для SMTP не подходит. Необходимо включить
двухэтапную аутентификацию и создать отдельный пароль приложения. Пароль,
который ранее был опубликован в issue, следует считать скомпрометированным и
заменить.

## Почему браузер показывает 503

`POST /api/email/resend` получает правильный адрес получателя, создаёт новый
токен и вызывает SMTP-отправку. Если подключение, STARTTLS, аутентификация или
передача письма завершается исключением, endpoint намеренно возвращает
безопасный ответ `503 verification_email_delivery_failed`. Поэтому 503 означает
не ошибку frontend и не неверный email получателя, а сбой внешней SMTP-операции.

Текущая реализация записывает в backend-лог этап сбоя (`connection`,
`starttls`, `authentication` или `send`), класс исключения, SMTP-код и ответ
сервера. Без этого production-лога нельзя достоверно выбрать между оставшимися
причинами, например неверным паролем приложения и сетевой блокировкой порта.

## Проверка фактически запущенной конфигурации

Docker Compose передаёт `.env` в контейнер только при его создании. После
изменения SMTP-настроек backend необходимо пересоздать:

```bash
docker compose up -d --force-recreate backend
docker compose exec backend env | grep -E '^(EMAIL_BACKEND|SMTP_HOST|SMTP_PORT|SMTP_SECURITY|SMTP_TIMEOUT_SECONDS|SMTP_USERNAME|SMTP_FROM_EMAIL)='
docker compose logs --since=10m backend
```

Не следует выводить `SMTP_PASSWORD` в терминал или прикладывать его к issue.
После повторной отправки нужно найти строку
`Verification email delivery failed`. Поле `stage` однозначно показывает:

- `connection` — DNS, сеть, порт или недоступность `smtp.gmail.com`;
- `starttls` — ошибка согласования TLS;
- `authentication` — неверный логин/пароль приложения или запрет SMTP со стороны Google;
- `send` — сервер отклонил отправителя, получателя или само письмо.

Успешная попытка заканчивается строкой
`Verification email accepted by SMTP server`.

## Проверка реализации

В репозитории уже есть автоматические тесты, которые проверяют:

- отклонение email-адреса в `SMTP_HOST`;
- подключение к заданному хосту и порту;
- STARTTLS и implicit TLS;
- SMTP-аутентификацию и адрес получателя;
- регистрацию, повторную отправку и смену токена;
- безопасный ответ 503 и подробный backend-лог;
- сокрытие пароля и токена в логах.

Таким образом, установленная программная причина исходного сбоя — неверный
`SMTP_HOST`. Если после исправления и пересоздания контейнера остаётся 503,
конкретная внешняя причина находится в уже добавленном поле `stage` и SMTP-коде
backend-лога.
