# Обзор проекта Kral для следующего агента

> Актуально для состояния ветки `main` на 18 июля 2026 года (коммит `d743f80`).
> Этот файл — не пользовательская инструкция, а подробный вводный контекст для
> разработчика или другого AI-агента, которому предстоит менять приложение.

## 1. Что это за приложение

Kral — русскоязычный веб-помощник для открытого D&D 2014-проекта «Эпоха
Катастроф». Он хранит аккаунты, персонажей, листы и инвентари, автоматизирует
внутриигровой календарь, поиск и продажу предметов, карму, набор на игры и
административный учёт. Это уже не пятистраничный прототип из `AGENTS.md`, а
мультипроектная система: один аккаунт может входить в несколько изолированных
игровых проектов с разными ролями, балансом кармы, персонажами и настройками.

Интерфейс и сообщения в основном русские. Денежная система — золото, серебро и
медь; при атомарных расчётах backend переводит всё в медь (`1 зм = 10 см = 100
мм`). Игровая эпоха начинается `2025-06-01`: дата появления персонажа или юнита
не может быть раньше неё.

## 2. Техническая архитектура

- Backend: Python, FastAPI, SQLAlchemy и PostgreSQL. Точка входа — `app/main.py`,
  API разбито по файлам `app/api/*.py`, модели — `app/models/*.py`, схемы
  Pydantic — `app/schemas/*.py`.
- Frontend: React 18 + TypeScript + React Router + Axios + Tailwind/Vite. Почти
  весь UI находится в одном крупном файле `app/src/main.tsx`; типы и API-клиент
  — в `app/src/api.ts`, стили — в `app/src/styles.css`.
- Аутентификация: JWT Bearer. Токен хранится в `localStorage`; выбранный проект
  также хранится там. Axios добавляет `Authorization` и `X-Project-ID`.
- Realtime: один WebSocket `/api/ws?token=...&project_id=...` на вкладку.
  Успешные мутации рассылают проектные события, после которых нужные экраны
  перечитывают данные. Реестр соединений находится в памяти процесса, поэтому
  несколько backend-worker требуют внешнего pub/sub.
- Развёртывание: локально `npm run dev` запускает FastAPI и Vite; production
  build создаёт `dist/`. Docker Compose поднимает PostgreSQL, FastAPI и nginx;
  стандартная production-конфигурация не публикует порт FastAPI наружу.
- Схема БД не управляется Alembic. `app/main.py` при старте вызывает
  `Base.metadata.create_all()`, затем выполняет большой набор PostgreSQL
  `ALTER TABLE`/backfill-миграций и создаёт индексы. Любое изменение модели
  нужно согласовывать с этой startup-миграцией и проверять как на пустой, так и
  на старой базе.
- Тесты: Python API/integration-тесты в `tests/test_*.py`, Node source-contract
  тесты в `tests/*.test.mjs`; обязательные локальные команды — `pytest`,
  `npm test`, `npm run build`.

## 3. Сквозные правила безопасности и области данных

Все игровые данные относятся к проекту. После входа пользователь обязан выбрать
проект на `/projects`. Почти каждый gameplay-запрос требует `X-Project-ID`;
backend разрешает доступ только через `ProjectMembership` именно выбранного
проекта. Нельзя полагаться только на скрытые кнопки: проверка проекта, владельца
персонажа и роли должна оставаться на API-границе.

Глобальный `owner` видит все проекты. Остальные роли проектные, от старшей к
младшей: `project_owner`, `head_admin`, `admin` (ведущий), `technician`,
`player`. Техник выдаёт ресурсы, смотрит логи и редактирует персонажей; ведущий
получает игровые административные действия; главный администратор управляет
нижестоящими ролями и настройками; владелец проекта стоит выше него. Глобальный
owner может назначать любые роли. Неглобальный администратор не может назначить
равную/старшую роль или изменить равного/старшего участника.

Создание аккаунта требует уникальных username/email, пароля от 6 символов и не
более 72 UTF-8 байт. Email нужно подтвердить одноразовой 24-часовой ссылкой.
Восстановление пароля также использует одноразовый 24-часовой токен; в БД
хранятся только SHA-256-хэши токенов. Login, registration и password reset
ограничены по IP/идентификатору; тело запроса ограничено 1 MiB, чат — 2000
символов, заметки инвентаря — 10000. SMTP имеет режимы `console` и `smtp` и
подробное безопасное логирование стадий без пароля.

Функции проекта хранятся в JSON `Project.features`. Флаги: `shop`, `market`,
`karma_shop`, `recruitments`, `personal_hirelings`, `simulacrums`,
`leaderboard`, `karma`, `karma_logs`, `character_transfers`, `market_logs`,
`logs`. Выключенная функция исчезает из навигации и должна быть запрещена
backend-зависимостью `require_feature`, а не только frontend-условием.

## 4. Карта экранов и поведения

### 4.1 Публичная аутентификация

- `/login`: username/email + пароль, вход, ссылки на регистрацию и сброс
  пароля. Успех сохраняет JWT и ведёт к выбору проекта. Ошибки локализованы;
  неподтверждённый email получает отдельное сообщение и возможность повторной
  отправки письма.
- `/register`: username, email, пароль; создаёт аккаунт-player и сообщает о
  письме подтверждения. Пароль в browser storage не сохраняется.
- `/verify-email`: берёт token из query string, подтверждает адрес и ведёт ко
  входу.
- `/forgot-password`: принимает email и всегда показывает одинаковый ответ,
  чтобы не раскрывать существование аккаунта.
- `/reset-password`: token из URL + новый пароль; после успеха старые reset
  токены недействительны.

### 4.2 Выбор проекта и общая оболочка

- `/projects`: список доступных проектов. Видимый проект можно открыть впервые;
  backend тогда создаёт membership с ролью player. Скрытый проект остаётся
  доступен прежним участникам и глобальному owner, но не обнаруживается новыми
  пользователями.
- После выбора открывается `/about`. Верхняя панель содержит «Назад», название
  проекта, селектор проекта, меню, «О проекте», персонажей, чат, набор на игры,
  профиль, условные admin/settings/project-management и logout. «Назад» идёт по
  истории приложения, а без неё безопасно возвращает в главное меню.
- `/`: плиточное главное меню и карточка текущего пользователя (username, email,
  роль, проектная карма). Плитки функций зависят от feature flags.

### 4.3 «О проекте» и публикации

`/about` состоит из двух независимых областей: лента публикаций слева и блок
«Об авторе» справа. Публикация имеет заголовок, Markdown-содержимое и позицию;
ссылки открываются в новой вкладке. Глобальный owner, project owner и head admin
могут создавать, редактировать, удалять и менять порядок публикаций, а также
редактировать авторский блок. Пустые области показывают понятные заглушки.

### 4.4 Персонажи

- `/characters`: до 10 собственных персонажей. Карточка показывает имя,
  основной класс, уровень, расу, подкласс и статус жизни; отсюда открываются
  лист, редактирование и создание.
- `/characters/new`: имя, один или несколько классов с уровнями, подкласс, раса,
  предыстория, путь, дата появления, HP, временные HP, КД, скорость, шесть
  характеристик, расследование и владение шестью спасбросками. Первый класс —
  основной, общий уровень равен сумме уровней классов, максимум 20; одинаковые
  классы нельзя повторять.
- `/characters/:id/edit`: владелец правит те же игровые поля, кроме даты
  появления и общего уровня. При мультиклассе сумма классов обязана совпадать с
  уже имеющимся общим уровнем; уровень повышает администратор/XP-механика.
- `/characters/:id`: подробный лист. Верх показывает классы, подкласс, расу,
  предысторию, путь, дату появления, HP/temp HP, КД, скорость, уровень, XP,
  бонус мастерства и статус жизни. Шесть характеристик кликабельны и бросают
  `d20 + floor((score-10)/2)`. Спасбросок добавляет бонус мастерства при
  владении. Бонус мастерства: `2 + floor((clamp(level,1,20)-1)/4)`.
- Навыки: все 18 стандартных D&D-навыков. Владение добавляет бонус мастерства,
  компетентность — двойной; backend рассчитывает и сохраняет бросок. Игрок
  управляет собственными владениями/компетентностями.
- Атаки: строки с названием, бонусом атаки и текстом урона. Можно добавить,
  изменить, удалить, бросить атаку (`d20 + attack_bonus`) и произвольный урон
  по допустимой dice-формуле; результаты публикуются в канал бросков.
- Мёртвый персонаж остаётся видимым, но игровые действия, которым нужен живой
  персонаж, запрещены. Воскресить может администратор либо сам игрок через
  Karma Shop в допустимом диапазоне уровней.

### 4.5 Инвентарь и переводы

На листе справа находятся кошелёк, заметки и предметы. Предмет содержит name,
rarity и `is_consumable`. Игрок может сохранить заметки, удалить предмет или
перейти к его продаже. При включённом `character_transfers` можно переводить
золото/серебро/медь и предметы другому живому персонажу проекта; получатель
может принадлежать другому игроку. Backend проверяет отправителя, получателя,
остаток и фактическое наличие предмета, выполняет операцию атомарно и пишет
transfer log.

### 4.6 Календарь и работа

На листе персонажа есть календарная панель с общей шкалой от даты появления до
текущего дня: занятые и свободные дни, журнал интервалов и пагинация по 10
записей. Интервалы включают обе границы; пересечение записей одного актёра
возвращает `409`, соседние интервалы допустимы. Игрок может добавить занятость
своему персонажу, но не редактировать и не удалять существующую запись.
Администратор может добавлять, менять и удалять записи любого персонажа.

Если проект включает личных наёмников/симулякров и администратор выдал юнит,
у него своя дата появления, расследование, свободные дни и отдельный календарь.
Игрок его только просматривает; ручное управление юнит-календарём — admin-only.

Работа резервирует период свободных дней, рассчитывает доход по таблице
владения инструментом в `app/core/calendar.py`, зачисляет точную сумму в
кошелёк и создаёт finance/calendar audit entries. Игрок не отменяет завершённую
работу. Администратор может удалить её: доход атомарно списывается; если он уже
потрачен, отмена получает `409`.

### 4.7 Магический магазин

`/shop` имеет вкладки «Купить» и «Продать».

При покупке можно искать каталог `magicvariants.json` по имени, редкости и типу
или ввести разрешённый предмет вручную; каталог магазина принимает только
обычные, необычные и редкие варианты. При продаже выбирается реальный предмет
из инвентаря. Далее выбираются собственный живой персонаж и искатель:
персонаж, личный наёмник, симулякр или платный наёмник.

Формула поиска:

| Редкость | DC | Длительность при успехе | При провале | Базовая цена | Расходник |
| --- | ---: | --- | ---: | ---: | ---: |
| Обычный | 5 | `1d4` дней | 4 дня | 100 зм | 50 зм |
| Необычный | 10 | `1d8` дней | 8 дней | 500 зм | 250 зм |
| Редкий | 15 | `1d12` дней | 12 дней | 5000 зм | 2500 зм |

Проверка — `1d20 + modifier >= DC`. Персонаж использует своё расследование,
юниты — своё; эти три актёра не платят золото, но занимают выпавшие дни в своём
календаре даже при провале. Платный наёмник дней календаря не тратит:

| Уровень | Модификатор | Цена в день |
| --- | ---: | ---: |
| Плохой | +0 | 1 зм |
| Хороший | +4 | 5 зм |
| Компетентный | +6 | 10 зм |
| Эксперт | +8 | 25 зм |

Скорректированный price roll — clamp(`1d100 + rarity modifier`, 1, 100), где
обычный получает +10, необычный 0, редкий −10. Для покупки диапазоны дают
множитель: 1–20 → 1.500–2.000; 21–40 → 1.000–1.490; 41–80 → 0.750–0.990;
81–90 → 0.500–0.740; 91–100 → 0.300–0.500. Для продажи: 1–20 → 0.300–0.500;
21–42 → 0.500–0.750; 43–82 → 0.750–0.900; 83–92 → 0.900–1.250; 93–100 →
1.250–1.600. Цена — округлённая базовая цена × множитель, минимум 1 зм.

Результат показывает raw/total roll, modifier, DC, дни, price roll, множитель,
цену и плату наёмнику. Поиск создаёт одноразовый `ShopQuote`. Подтверждение
повторно проверяет владельца, баланс/предмет и атомарно помечает quote
использованным, чтобы двойной клик не провёл операцию дважды. Покупка списывает
цену предмета (а платному наёмнику — ещё стоимость дней) и добавляет предмет;
продажа удаляет предмет, начисляет цену и учитывает плату наёмнику. Можно
продолжить поиск, создав новую котировку.

### 4.8 Рынок

`/market` — простая гарантированная продажа без поиска: выбрать свой предмет,
ввести положительную цену в золоте и подтвердить. Предмет удаляется, кошелёк
пополняется, операция попадает в market-sales audit log. Это отдельная механика
от вероятностной вкладки «Продать» магического магазина.

### 4.9 Карма, профиль и лидерборд

- `/profile`: username, email, баланс проектной кармы и сохранённые покупки/
  открывашки. Карма глобального аккаунта не используется как единый баланс:
  фактический баланс находится в membership конкретного проекта.
- `/karma-shop`: три секции. XP стоит 5 кармы за единицу и выдаётся собственному
  персонажу. Открывашка выбирается из предустановленного списка либо задаётся
  именем/стоимостью и сохраняется в профиль. Воскресить можно мёртвого
  персонажа уровня 1–5 за 5 кармы или 6–10 за 10; 11+ недоступны. Списание и
  эффект атомарны, покупка логируется с actor, user, персонажем и его уровнем.
- `/leaderboard`: responsive-таблица rank, username, karma, упорядоченная по
  убыванию проектной кармы.

### 4.10 Чат и броски

`/chat` имеет вкладки «Общий чат» и «Броски». История загружается страницами до
200 сообщений. Обычный текст сохраняется в general; команда `/r NdM` или
отдельный endpoint броска генерирует кости и сохраняет результат в rolls.
Поддерживаются положительные count/sides в установленных схемой пределах.
Пользователь видит realtime-обновления. Свои сообщения можно удалять; любое
сообщение может удалить project admin. Backend проверяет эти права.

### 4.11 Набор на игры

`/game-recruitments` — список объявлений с серверной пагинацией (page/page_size),
статусом и встроенным чатом каждого объявления. Ведущий создаёт объявление с
названием, описанием и датой/временем, меняет статус и удаляет его. Игрок
записывает одного собственного живого персонажа. Автор объявления видит заявки,
выбирает участников и публикует состав; системные сообщения о записи и составе
сохраняются в announcement chat. Чат использует cursor-based загрузку старых
сообщений при прокрутке вверх; пользователь удаляет свои сообщения, admin —
любые.

### 4.12 Правила и справочники

- `/server-rules`: упорядоченные публикации. Все блоки изначально свёрнуты;
  состояние раскрытия хранится по странице. Администраторы создают, правят,
  удаляют и двигают блоки вверх/вниз.
- `/approved-homebrew`: таблица с колонками «Название», «Тип», «Карма / Бан»,
  «Источник / Ссылка», «Примечания» и admin-actions. Есть поиск по названию,
  фильтр типа, фильтр karma/banned и сортировка по каждой предметной колонке.
  Запись взаимоисключающе либо запрещена, либо имеет неотрицательную стоимость
  кармы. Admin CRUD и ручной порядок; сортировка не мутирует сохранённый порядок.
- `/illegal-items`: таблица «Название», «Редкость», «Ссылка», «Источник» и
  admin-actions. Поиск по имени, фильтр и сортировка редкости/имени. Редкости:
  обычный, необычный, редкий, очень редкий, легендарный, артефакт, варьируется.
  Admin CRUD и изменение порядка.

### 4.13 Административные экраны

- `/admin-menu`: центральные ссылки на управление, профили игроков и журналы;
  элементы учитывают feature flags и уровень роли.
- `/admin`: две пагинированные области (пользователи и все персонажи, размер
  страницы выбирается). Пользователи показывают username/email/подтверждение,
  проектную роль, карму и число персонажей. Доступные действия: подтвердить
  email, изменить роль в рамках иерархии, прибавить/вычесть карму с обязательной
  причиной; глобальный owner может удалить другой аккаунт, если тот не владеет
  проектами. Каскадное удаление включает его игровые данные.
- Таблица всех персонажей показывает владельца, имя, классы, уровень, дату
  появления и свободные дни персонажа/выданных юнитов. Из неё открывается
  `/admin/characters/:id`.
- `/admin/characters/:id`: полный редактор чужого персонажа, включая XP,
  уровень/классы, характеристики, жизнь, дату появления, личного наёмника и
  симулякра (enabled, дата, investigation). Администратор выдаёт XP, валюту и
  предмет с обязательной причиной, воскрешает и управляет тремя календарями.
  XP повышает уровень циклом: для перехода с L на L+1 требуется L+1 XP, остаток
  переносится; максимум 20. Автоповышение добавляет уровни последнему классу.
  Удалять персонажей могут только owner/head admin.
- `/admin/player-profiles`: карточки пользователей с персонажами и открывашками;
  admin может бесплатно добавить именованную открывашку или удалить существующую.
- `/project-settings`: owner/project owner/head admin включает feature flags
  текущего проекта.
- `/project-management`: только глобальный owner; таблица всех проектов,
  создание name/optional slug, переключение доступности и удаление не-default
  проекта. Удаление удаляет только данные цели и создаёт неизменяемый audit log.

Журналы — responsive-таблицы с фильтрами и атрибуцией «кто выполнил» отдельно
от получателя:

- `/admin/grant-logs`: дата, администратор, игрок/персонаж, операция (karma, XP,
  gold, item), величина/предмет и причина; фильтры по участникам, типу и датам.
- `/admin/shop-logs`: buy/sell, actor, игрок, персонаж, предмет/редкость, цена,
  наёмник и итог; фильтры и режим.
- `/admin/market-sales`: дата, actor, игрок, персонаж, предмет, начисленное золото.
- `/admin/karma-shop-logs`: дата, actor, игрок, персонаж, тип, название,
  стоимость и зафиксированный уровень.
- `/admin/transfer-logs`: дата, actor, отправитель/получатель, персонажи, тип,
  валюта либо предмет; фильтры.
- Calendar audit endpoint существует и поддерживает фильтры character/user/
  action/date, хотя отдельный frontend-route в текущем Router не зарегистрирован.

## 5. Основные сущности БД

- `User`: username, email, bcrypt password hash, legacy/global role flags,
  email verification/reset hashes и сроки. Связан с персонажами, memberships и
  административными действиями.
- `Project`: name, slug, default/selectable, owner, JSON features/settings,
  creator content. `ProjectMembership`: user + project + project role + karma.
  `ProjectAboutPost` и `ProjectAuditLog` обслуживают страницу и удаление.
- `Character`: владелец/project, базовая биография, JSON class levels, level/XP,
  HP/temp HP/AC/speed, характеристики, investigation, JSON skill/save владения,
  death, дата появления, настройки двух юнитов. Связан с inventory, attacks и
  downtime entries.
- `Inventory`: кошелёк и notes, один на персонажа. `InventoryItem`: имя,
  редкость, consumable. `ShopQuote` — одноразовый результат поиска;
  `ShopTransactionLog`, `MarketSaleLog`, `TransferLog`, `AdminGrantLog` —
  неизменяемые операционные журналы.
- `DowntimeEntry`: actor type, inclusive dates, activity/details и данные дохода
  от работы. `CalendarAuditLog` фиксирует admin corrections.
- `CharacterAttack`: имя, attack bonus, damage text.
- `ChatMessage`: project/channel/user/text и dice metadata.
- `GameRecruitment`, application, participant и recruitment message: объявление,
  заявки, выбранный состав и отдельный чат.
- `ContentBlock`: page slug, position и JSON-подобные поля для правил,
  homebrew и illegal items.
- `KarmaPurchase`: проект, получатель, actor, optional character, type/name/cost,
  captured character level.

## 6. API по модулям

- `users.py`: registration, login, email verify/resend, forgot/reset password,
  current user.
- `projects.py`: список/выбор, CRUD/availability, settings, memberships/roles,
  project about.
- `characters.py`: CRUD собственных персонажей, transfer targets, ability/save/
  skill rolls.
- `inventory.py`: inventory/items/notes/currency, transfers, magic catalog,
  shop search/buy/sell, market sale.
- `attacks.py`: attack CRUD, attack/damage rolls.
- `calendar.py`: character/unit summaries, downtime/work CRUD и проверки дней.
- `chat.py`: leaderboard, project chat and dice.
- `recruitments.py`: announcements, applications, participants, nested chat.
- `content.py`: rules/homebrew/illegal-item CRUD and ordering.
- `karma_shop.py`: purchase list/openers, XP, opener/goods, resurrection.
- `admin.py`: users/characters/profiles, roles, resources, resurrection/deletion,
  all operational logs.
- `realtime.py`: authenticated project WebSocket.
- `shop.py`: legacy `/shop/buy`, `/shop/sell` и `/shop/search` API retained for
  compatibility; основной современный flow находится в `inventory.py` и
  использует persistent one-use quotes.

## 7. Что важно учитывать при следующих изменениях

1. Любой новый gameplay endpoint должен проверять JWT, `X-Project-ID`, feature
   flag (если применим), project_id каждой сущности и ownership/role.
2. Карма — `ProjectMembership.karma`, а не один общий `User.karma`. Legacy-поля
   существуют ради миграции/совместимости; не смешивать области.
3. Скрытие UI не является авторизацией. Для каждого admin/player различия нужен
   backend-тест прямого запроса.
4. Денежные и магазинные операции должны быть транзакционны, защищены от
   повторного подтверждения и оставлять actor-aware audit log.
5. Календарные даты включительны; проверять пересечения отдельно для character,
   personal hireling и simulacrum. Не списывать дни платному наёмнику.
6. При изменении level синхронизировать class levels. При создании total — сумма;
   при XP auto-level растёт последний класс; максимум 20.
7. Frontend монолитен: одинаковые формы/типы часто встроены в `main.tsx`.
   Перед рефакторингом сохранить source-contract тесты — многие Node tests
   намеренно проверяют конкретные маршруты, labels и защитные условия.
8. Realtime-событие не заменяет устойчивое состояние: mutation сначала commit,
   затем publish; клиент по событию перечитывает API.
9. Изменение SQLAlchemy-модели без startup migration сломает существующую БД.
   Удаление project/user требует перечислить все зависимые таблицы, потому что
   исторически не везде есть согласованный ON DELETE CASCADE.
10. `magicvariants.json` — внешний каталог большого размера; магазин фильтрует
    допустимость, редкость и известные исключения. Нельзя доверять item name/
    rarity с frontend.
11. Проверять responsive-таблицы и мобильную верхнюю панель: проект уже имел
    отдельные регрессии переносов, горизонтального скролла и кнопки «Назад».
12. После изменения запускать `pytest`, `npm test`, `npm run build`; для UI также
    реальный браузер и screenshot. Для изменений схемы дополнительно тестировать
    запуск на чистой PostgreSQL и миграцию копии старой схемы.

## 8. Известные технические особенности и риски

- `app/src/main.tsx` превышает 4000 строк, а `app/main.py` содержит сотни строк
  ручных миграций. Это повышает связанность и риск конфликтов; новые крупные
  функции лучше выделять постепенно, не смешивая с функциональным изменением.
- Есть современный quote-based магазин и legacy `app/api/shop.py`. Перед
  удалением legacy API нужно найти внешних клиентов и тесты; совпадение URL не
  означает одинаковую семантику.
- WebSocket registry process-local: при `WEB_CONCURRENCY > 1` событие увидят не
  все соединения без Redis/Postgres pub/sub.
- README содержит широкий operational guide, но `AGENTS.md` описывает ранний
  прототип и уже неполон. Для фактического поведения источником истины являются
  API, схемы, модели и тесты; этот обзор следует обновлять вместе с крупными
  продуктовыми изменениями.
- Отдельная UI-страница calendar audit logs отсутствует, хотя backend endpoint
  и схема журнала есть. Не обещать навигацию к ней без добавления route/page.

## 9. Быстрый маршрут знакомства с кодом

Начать с `app/src/main.tsx` внизу (Router), затем прочитать нужную page-функцию и
её методы API в `app/src/api.ts`. На backend найти route через `rg
'@router\.(get|post|patch|delete)' app/api`, затем прочитать Pydantic-схему,
SQLAlchemy-модель и тесты по номеру функции/предметной области. Для сквозных
прав обязательно просмотреть `app/api/projects.py`, `app/core/roles.py`,
`app/api/users.py`, `app/main.py` и realtime middleware. README полезен для
deployment-контекста, но точные формулы магазина находятся в
`app/api/inventory.py`, календаря — в `app/api/calendar.py` и
`app/core/calendar.py`, а XP/админские права — в `app/api/admin.py`.
